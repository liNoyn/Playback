1. **録画データは常に「生」を残す**（時間情報を足すだけ）。補正は後段（FlashBridge・再生）で選べるようにして、アルゴリズムを後から直せるようにする。

3. 実機でしか分からないこと（サーバー tick の取得方法）は、**設計を固める前に実験（Phase 0）**で確かめる。

## 3. A. tick 速度の正規化

### 3.1 何を直したいか
サーバーが重いと（例: 10 TPS）、サーバー側のゲーム内時間は実時間の半分の速さで進む。クライアントは 20 tick/秒で動き続けるので、今の録画は **「遅い世界」をそのまま 20 tick/秒で保存**し、再生すると、動きが重く／とびとびになる。

目標: **リプレイの 1 tick ＝ サーバーの 1 tick（ゲーム内時間 1/20 秒）** とし、ラグの間も通常速度で見られるようにする。

| 現象 | 今の記録（クライアント tick） | 正規化後（サーバー tick） |
|---|---|---|
| サーバー 10 TPS（2 倍遅い） | 世界が 2 倍ゆっくり動く | 通常速度。2 つのクライアント tick を 1 つに束ねる |
| ラグの後に追いつく（バースト） | 一瞬で瞬間移動 | 追いついた分の tick を滑らかに補間して展開 |
| サーバー停止（数秒） | 空白が続く | 範囲外として扱い、時間を進めない |

### 3.2 方式：非破壊（生の時間情報を残し、後段で補正）
- Recorder は、各クライアント tick に **`tick_info`** を 1 件追加する新アクションを書く。
  - 内容: 実時間（単調増加のマイクロ秒）、サーバー tick の推定値（取れなければ −1）、推定の根拠（種別）、品質フラグ。1 tick あたり約 12 バイト（1 分で 約 14KB）。
  - 既存の `next_tick` は変えない。
- **補正は FlashBridge の変換時に行う**（`TickNormalizer`）。同じ生データから、ユーザーの選択に応じて 3 種類を出せる。

| モード | 1 リプレイ tick | 用途 |
|---|---|---|
| **ゲーム時間（正規化）** 既定 | サーバー 1 tick | 動画編集向け。ラグが消える |
| 実時間 | 実時間 50ms | 見たままの再現（ラグも再現） |
| 生（現行） | クライアント 1 tick | 互換・検証 |

- 後段でアルゴリズムを直せる（録画をやり直さなくてよい）。判定を誤っても「生」に戻せる。
- Playback 自身の再生でも同じ正規化を使えるように、Phase 3 以降は「正規化して保存」操作（新しいリプレイを書き出す）を提供する。再生エンジン（`ReplaySession`）は触らない。

### 3.3 サーバー tick をどう得るか（Phase 0 の実験）
候補を**全部記録して比較する診断モード**（`/playback debug ticks`）を最初に作り、ラグのかかったサーバーで実測する。

| 候補 | 内容 | 懸念 |
|---|---|---|
| 1. `ClientLevel::getCurrentServerTick()` | クライアントが持つ「サーバー tick」の推定 | 実際はクライアント tick＋固定のずれで、サーバー負荷を反映しない可能性 |
| 2. `SyncWorldClocks` / `SetTime` の時刻値 | サーバーのワールド時計 | 送信間隔が長い。クライアントが自前で進める可能性 |
| 3. `ServerStats` パケット | サーバー処理時間の統計 | 通常のサーバーが送るか不明 |
| 4. **到着パターンからの推定（本命候補）** | サーバーは 1 tick の更新をまとめて送る。**更新の「まとまり」の到着間隔**＝サーバー tick 間隔。エンティティ移動・ブロック更新などの到着クラスタを数える | ネットワークの揺らぎ（ジッター）と区別が必要。しきい値の調整 |
| 5. エンティティ移動の更新周期 | 他エンティティの `MoveActor*` が来る周期 | 動かないワールドでは使えない |

**判定基準（実験の合格条件）**: 人為的にラグを作ったサーバー（例: 負荷をかけて 10 TPS にしたもの）で、推定 TPS が実際の値と **±1 TPS**、ラグの開始/終了が **±1 秒**で分かること。合格した候補を主、次点を副、4 を最後の砦として「推定器の連鎖」にする（`ServerTickSource`、品質フラグで出所を残す）。

### 3.4 正規化アルゴリズム（FlashBridge: `TickNormalizer`）
入力: クライアント tick `i` ごとの `(wallµs_i, S_i)`（`S_i` はサーバー tick 推定）と、そのティックのアクション。
出力: サーバー tick `s` ごとの tick。

1. `S_i` を **単調増加に整える**（逆戻りは前の値に固定）。品質が低い区間は `wallµs` から `S` を補う（20 tick/秒で外挿）。
2. **束ねる**（`S` が進まないクライアント tick が続く）: 同じ `s` に属する tick のアクションを順番どおり連結する。
   - 状態型（エンティティ位置・自プレイヤー位置）は**最後の値だけ**を残す。
   - イベント型（パケット）は順番どおり全て残す。
3. **展開する**（`S` が `k > 1` 進んだ）: `k−1` 個の空 tick を挟み、エンティティ位置は直前と今回の間を**線形補間**して各 tick に出す（追いつき時に瞬間移動して見えないようにする）。
4. **上限**: `k` が閾値（既定 200＝10 秒）を超えたら「断絶」とみなし、補間せず 1 tick で進める（サーバー停止・再接続など）。
5. 実時間は `real_time_clock_optional`（Flashback）として並行して書く → 編集側で実時間の経過が分かる。
6. **ラグ区間の自動マーカー**: 推定 TPS が 15 未満の状態が 2 秒以上続いたら「ラグ（≈10 TPS）」マーカーを付ける。

**不変条件（テストで担保）**: 出力の総 tick ＝ `S_last − S_first`（断絶を除く）／アクションの順序と個数が（束ね・補間を除き）保存される／`S` が一定（ラグ無し）の録画は**現行の出力とバイト単位で同じ**になる。

### 3.5 データ形式の変更
| 変更 | 内容 | 互換性 |
|---|---|---|
| 新アクション `tick_info` | 上記ペイロード。各クライアント tick の `next_tick` の**直前**（その tick の終わりの値。FlashBridge が先読みせずに済む） | 本家 Playback は未知のアクション名で読み込みに失敗する → 設定「互換形式で録画（tick_info を書かない）」を用意。フォーク同士は問題なし |
| `metadata.json` | `features: ["tick_info"]`、`tickSource`（使った推定器）を追加 | 本家は未知キーを無視 |
| ライブ配信プロトコル | 変更なし（`CHUNK_DATA` は録画バイト列そのもの） | — |

### 3.6 設定
`timeNormalization`: `"game"`（既定）／`"wall"`／`"raw"`、`lagMarkers`（既定 on）、`lagThresholdTps`（15）、`maxGapSeconds`（10）。録画時の設定は「記録するか」（`tick_info` 有無）、変換時の設定は「どう出すか」。

## 4. B. 録画の操作系

### 4.1 入口
| 入口 | 動作 | 実装の方針 |
|---|---|---|
| ホットキー | 既定: `F8` 録画開始/停止（出力は設定の既定モード）、`Ctrl+F8` 出力モードを選んで開始、`Shift+F8` 一時停止/再開、`F7` マーカー、`F6` パネル（ゲームの既定キーとの衝突は実機で確認。**すべて変更可**） | 既存の WndProc フック（`ReplayMouseHook`）にキー入力を追加。チャット・看板入力など**文字入力中は無効** |
| 画面内 HUD | 録画中の小さな表示（右上）。クリック不要 | 既存の ImGui 描画（D3D11/12 フック）を、リプレイ時だけでなくプレイ中も使えるようにする |
| 操作パネル | `F6`、またはポーズメニューの「Playback」ボタン | ポーズメニュー内なら Bedrock がマウスを解放済み → 追加のカーソル制御が要らない（安全）。ホットキーで開く場合は既存のマウス所有ロジックを流用（要検証） |
| コマンド | 既存の `/record ...` は残す。`/record start [playback\|both\|flashback]`（省略時は設定の既定）、`/record marker <名前>`、`/record status` を追加 | 既存 |
| メインメニュー | 既存の「リプレイ」ボタン（一覧へ）は残す | 既存 |

### 4.2 録画の状態
`待機 → 録画中 ⇄ 一時停止 → 保存中 → 完了（／失敗）`。各状態を HUD・パネル・トーストで同じ言葉で表示する。「保存中」は書き出しと FlashBridge の変換を含み、完了時に「Flashback に追加しました（開く／フォルダ）」を出す。

### 4.3 HUD の中身
```
 ● REC  12:34   1.8 GB 空き   ⇄ FlashBridge 変換中 ✓      ← 通常
 ● REC  12:34   TPS 11.2 ⚠ ラグ                          ← サーバーが重いとき
 ❚❚ 一時停止  12:34                                       ← 一時停止
```
表示項目（個別に on/off）: 経過時間、空き容量、サーバー TPS、FlashBridge 状態、マーカー数。サイズ・不透明度・位置（四隅）を設定可。画面キャプチャ（OBS 等）に映るため、**「録画インジケータを非表示」**の設定を用意する。

## 5. E. 追加機能の設計（要点）

### 5.1 インスタントリプレイ（直近 N 分の保存）
- 録画方式「連続録画」と「バッファ」を切り替える。バッファは**常時録画**し、古い区間を捨てる。
- 既存構造（約 5 分ごとに完全なスナップショットから始まるチャンク）を活かす: バッファ時は**チャンクを短く（既定 30 秒）**し、保持時間を超えた古いチャンクを破棄する。各チャンクが単独で再生可能なので、破棄しても残りは壊れない。
- 課題: チャンクキャッシュ（`level_chunk_caches`）は追記専用で、チャンク間で共有している。→ **保存時に作り直す**: 残すチャンクが参照するエントリだけを新しいキャッシュに詰め直し、`level_chunk_cached` の番号を振り直す（既存の書き出し処理と同じ形式）。常時のディスク使用は、バッファ上限（既定 2GB）で頭打ち。
- 保存は `F8`（開始/停止）とは別のキー（既定 `F9`「直近を保存」）。保存中も録画を続ける。

### 5.2 自動録画ルール
ルール = 条件（ワールド名／サーバーアドレス／ディメンション）＋動作（自動で録画／確認トースト／無視）＋出力モード（§5.7、省略時は既定）。入室（ローカルプレイヤー生成）で評価、退出で自動停止。複数ルール、優先順位あり。

### 5.3 クラッシュ復旧
- 一時フォルダ（`data/temp/<uuid>`）に残った録画を起動時に走査。`metadata.json`（無ければ `.old`）と `chunk_*.bin` から、通常の書き出し（`ReplayExporter`）を再実行。
- 一覧に「未保存の録画が見つかりました（3 件）→ 復元」を出す。復元後は FlashBridge の変換も依頼できる。
- **復元できる範囲**: 現状、チャンクファイルは約 5 分ごと（と停止時）にしか書かれないので、落ちた時点から**最大 5 分前まで**が失われる。これを縮めるため、開いているチャンクを 30 秒ごとに「途中までのチャンク」として書き出す（`chunk_N.part`、完了時に `chunk_N.bin` へ置き換え）。形式は従来の `chunk_N.bin` と同じで、復元時に末尾の不完全なアクションを切り捨てる。

### 5.4 ディスク保護
録画中に空き容量を監視（既定 5 秒ごと）。しきい値（既定 3GB）で警告、（既定 1GB）で自動停止して**保存を完了**させる。整理: 保存先の合計が上限（既定 50GB）を超えたら古い順（お気に入り・タグ付きは除外）に削除の確認を出す（自動削除は既定オフ）。

### 5.5 FlashBridge 連携の表示（プロトコル v2）
現状は Playback → 変換ツールの一方向。**変換ツール → Playback の `STATUS` フレーム**（JSON、約 1 回/秒）を追加する。
```
{ "state": "converting", "ticks": 18432, "behindTicks": 12, "queuedMB": 3.1,
  "outputs": ["Replay Camera 01"], "lastResult": null, "warnings": 0 }
```
Playback は専用スレッドで受信するだけ（録画側の処理には触れない）。非対応の相手（`protocol:1`）には送らない（HELLO のバージョンで判断）。

### 5.6 マーカーと Flashback への受け渡し
マーカー = tick 番号・名前・色。`metadata.json` の `markers` に保存。FlashBridge は Flashback の `markers`（`replayMarkers`）へ変換。正規化後の tick 番号に自動で読み替える。

### 5.7 出力モード（Playback で撮る／Flashback にする）

**出力モード**（何を残すか）と**変換タイミング**（いつ変換するか）を、録画ごとに選べるようにする。

| 出力モード | 内容 | 残るもの | 向いている場面 |
|---|---|---|---|
| **Playback のみ** | 従来どおり。変換しない | Playback の録画 | FlashBridge 未導入／軽く撮りたい／Playback の編集機能で使う |
| **両方**（FlashBridge があれば既定） | Playback の録画を残しつつ、Flashback 用リプレイも作る | 両方 | 迷ったらこれ。変換が失敗しても元が残る |
| **Flashback のみ** | 手元に残すのは Flashback 用リプレイ。Playback の録画は**変換が検証できてから**期限つきで整理 | Flashback リプレイ（＋期限つきの元） | Flashback で編集するだけの人／容量を節約したい |

| 変換タイミング | 内容 |
|---|---|
| **録画中**（既定） | 今のライブ変換。停止した瞬間に Flashback 側が完成 |
| **停止後** | 録画中は何も流さず（ゲームへの負荷なし）、停止後に書き出された録画をまとめて変換。PC が非力なときや、録画中の CPU 使用を避けたいとき |

**指定の優先順位**（上が優先）: 録画開始時の指定（パネル／`/record start <mode>`／`Ctrl+F8`）＞ 自動録画ルール ＞ 設定の既定 ＞ FlashBridge が見つからないときは「Playback のみ」。出力先のインスタンスも録画ごとに上書きできる（パネルのチェックリスト。既定は FlashBridge の `config.json`）。時間の補正（§3）は Flashback への出力にだけ効く。

**仕組み**（既存の部品の組み合わせで実現できる）
- 「Playback のみ」＝ライブ配信を開始しない。
- 「録画中」＝今のライブ配信。
- 「停止後」＝ストリームは流さず、停止後に `HELLO(streamComplete:false)` ＋ `FINISH(replayFile)` だけ送る。これは今の**フォールバック経路そのもの**で、新しい変換コードは要らない。
- 「Flashback のみ」＝上記に加え、変換が成功したら元の録画を退避する（下記）。

**「Flashback のみ」の安全策**
1. **変換が検証できるまで元を消さない**。FlashBridge は書いた zip を開き直して、メタデータ・チャンク数・tick 数が録画と一致することを確かめ、STATUS の `lastResult` に `ok: true, verified: true` と出力一覧を載せる。Playback はこれを受け取ってから元を処理する。
2. 元は即削除せず、**退避フォルダ**（`data/trash`）へ移し、保持期間（既定 7 日）後に自動削除。保持は `7 日／常に残す／検証後すぐ削除` から選ぶ。
3. 変換が失敗・検証できなかった場合は、元をそのまま残して警告（トースト＋状態画面）。
4. ライブラリでは、各リプレイに「Playback」「Flashback 変換済み（インスタンス名）」のバッジ、退避中の元には「あと 6 日で削除」と「元を戻す」を表示。
5. モードは**録画開始時に固定**（録画中・一時停止中は変更不可）。途中で FlashBridge が落ちても、終了時のフォールバックで変換される。
6. FlashBridge が見つからないのに「両方／Flashback のみ」を選んだ場合は、開始時に「FlashBridge が見つかりません。Playback のみで録画します」と表示して**録画は止めない**。

**プロトコル**: HELLO に `outputMode`（`playback`/`both`/`flashback`）、`convert`（`live`/`afterStop`）、`targets`（任意：出力先の上書き）を追加。STATUS の完了通知に `verified` と出力一覧を追加（§5.5・§8.3）。

## 9. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| サーバー tick を取る方法が見つからない | A が成立しない | Phase 0 で判定。最悪でも「到着パターン推定」で実装し、品質フラグ付き・既定を「生」にもできる |

| プレイ中の ImGui 描画・入力フックで不安定になる／ゲームが重くなる | 最重要の安定性 | 既存のフック機構（リプレイ時に稼働実績あり）を流用。HUD は必要時のみ描画。**UI を丸ごと無効にする設定**を用意 |

| インスタントリプレイのキャッシュ詰め直しが重い | 保存に時間 | 保存はバックグラウンド。まず小さな区間（2 分）で実測 |
| Bedrock / LeviLamina の更新で内部 API が変わる | ビルド不能 | 内部参照は 1 か所（`TickClock` など）に集約し、取れないときは機能だけ止める |

## 11. テスト計画
- **単体（Java）**: `TickNormalizer`（束ね・展開・断絶・単調化・ラグ無しで出力同一）、`MarkerMapper`、設定の検証。**合成データ**で不変条件を機械的に確認。
- **単体（C++）**: 設定の読み書き／移行、推定器（記録した到着ログを入力にしたリプレイテスト）、ホットキー文字列の解析。
- **結合**: `simulate-live` に `tick_info` 付きの合成録画を流し、出力の tick 数と順序を検証。STATUS の往復。
- **出力モード**: 3 モード × 2 変換タイミングの組み合わせで、ストリームの有無・`FINISH` のみの依頼・検証後の退避・保持期間後の削除・FlashBridge 不在時の降格を確認。「Flashback のみ」で検証に失敗したとき、元が**必ず残る**こと。
- **実機**: ラグ再現サーバー（意図的に TPS を落とす）で A の合格条件、HUD/パネルの操作、フック安定性（1 時間連続録画でクラッシュ・FPS 低下なし）。
- **互換**: 互換形式の録画を本家 Playback 0.3.3 で再生。`protocol:1` の変換ツールとの接続。

- Playback 側の `settings.json` は機能名のキー（`liveStream`、`output`、`timeNormalization` など）を使い、製品名をキーに入れない。
- Playback フォークの画面・文言では「FlashBridge」と表記し、言語ファイルの 1 キー（`playback.flashbridge.name`）にまとめる。
- ライブ配信プロトコルは名前を含まない。変換ツールの版は STATUS の `converterVersion` で伝える（プロトコル v2）。
- リリース: FlashBridge は `flashbridge-<ver>-windows-x64.zip`、フォークは `Playback-live-stream-<ver>-windows-x64.zip`。

## 13. 決定事項（2026-10-15）
1. **正規化の既定モード**: ゲーム時間。
2. **ホットキーの既定**: F8 / Ctrl+F8 / Shift+F8 / F7 / F6 / F9（実機で衝突があれば変更）。
3. **本家との互換**: `tick_info` を既定で書く（`recording.compatibleFormat` で無効化できる）。
4. **GUI の入口**: ポーズメニューのボタン＋ホットキー。
5. **出力モードの既定**: 「両方」（FlashBridge が無ければ Playback のみ）。**「Flashback のみ」の元録画の保持期間は 7 日**。
6. **名前**: 変換ツールは FlashBridge のみ。以前の名前は一切使わない（§12）。
7. **着手順**: Phase 0 → 1 → 2 の順に実装。サーバー tick は、Bedrock パケットに載っている tick（`SetActorData` などの送信時サーバー tick）を主に使い、取れない区間は実時間と直近のレートで補う。
